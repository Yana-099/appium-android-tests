# Расширенное руководство для AI-агентов

## Назначение и границы

Это репозиторий мобильных Android UI-тестов на Python, pytest и Appium. Следуйте этому документу вместе с явной задачей пользователя; если они расходятся, остановитесь и запросите уточнение.

Этот документ не разрешает сам по себе добавлять новые обычные UI-сценарии или реализовывать AI-анализ падений: для них нужна отдельная согласованная задача.

## Уровень автономности (STOP & ASK)

- Свободно исследуйте код, документацию и существующее покрытие, затем предлагайте план изменений.
- Работайте только в отдельной task-ветке: `main` не изменяется напрямую. Для неоднозначной или крупной задачи согласуйте дизайн и план до написания кода.
- Запросите явное подтверждение до изменения `requirements.txt`, `pyproject.toml` или иных зависимостей; правки visual baseline; удалённых действий в Qase; `git commit`; `git push`; создания Pull Request.
- При конфликте правил, неясной области изменений или отсутствии стабильного пути реализации остановитесь и задайте один конкретный вопрос.

## Scope изменений и blast radius

- Меняйте только файлы, напрямую необходимые для поставленной задачи. Перед правкой перечислите затрагиваемые файлы и объясните их связь с задачей.
- Не рефакторите `pages/base_page.py`, `conftest.py`, `utils/`, `config/` или соседние Page Object «заодно». Для изменения общего слоя сначала объясните необходимость, возможный blast radius и получите явное согласование.
- Не удаляйте существующие `assert`, не добавляйте `@pytest.mark.skip` или `xfail`, не ослабляйте ожидаемые результаты и не снижайте пороги visual regression, чтобы сделать прогон зелёным.
- Если тест падает, сначала определите причину в приложении, тестовых данных, окружении или новом коде. Исправляйте источник проблемы, а не симптом.

## Карта проекта

- `pages/` — Page Object: локаторы, ожидания и повторно используемые UI-действия.
- `tests/` — сценарии, предусловия, проверки, Allure-метаданные и бизнес-шаги.
- `config/` — профили устройств, capabilities, настройки и разрешённые demo-данные.
- `conftest.py` — pytest-фикстуры, Appium-сессия, хуки и диагностика падений.
- `utils/` — изолированные помощники для Android, Allure, скриншотов и визуального сравнения.
- `tools/` — отдельные служебные скрипты (`analyze_failure.py`, `generate_from_qase.py`, `send_telegram_report.py`, `run_multi_device_demo.ps1`); токены и ключи читаются только из переменных окружения.
- `.github/workflows/` — CI и Telegram-уведомления GitHub Actions; это защищённая зона.

## Быстрые команды

```powershell
python -m pytest --collect-only -q
python -m pytest tests/unit tests/tools -q
python -m pytest tests/products/test_product_card.py --device pixel_api31 -v
python -m pytest -m smoke --device small_phone_api34 -v
```

Эти команды не включают `crash_demo`; для него требуется отдельный явный флаг из раздела «Защищённые операции».

## Локаторы и взаимодействие с UI

- Используйте только устойчивые Android-локаторы: `accessibility id`, фиксированный `resource-id`, стабильный test tag/content description либо уникальное неизменяемое имя. Предпочитайте `accessibility id`.
- `AppiumBy.ANDROID_UIAUTOMATOR` допустим только внутри `pages/` для устойчивой системной навигации, например `UiScrollable`; не используйте его для позиционного поиска или как обход отсутствующего стабильного идентификатора.
- Не используйте XPath, позиционные селекторы, текст, зависящий от локали, динамические идентификаторы или сгенерированные классы как основной локатор. Если стабильного идентификатора в приложении нет, остановитесь и запросите решение вместо создания хрупкого обхода.
- Не используйте `time.sleep()`. Ожидайте конкретное состояние через `WebDriverWait` и `expected_conditions` или методы ожидания `BasePage`.
- В `tests/` нельзя искать элементы или выполнять UI-клики напрямую через `driver.find_element`, `find_elements`, `click`, `send_keys` и аналогичные вызовы. Инкапсулируйте локатор, ожидание и действие в `pages/`.
- Системные lifecycle-действия (Back, блокировка, уведомление, ADB) не являются UI-поиском. Выносите их в выделенный page/helper-метод с понятным именем, а не смешивайте с проверками сценария.

## Архитектура тестов и зависимостей

- Перед созданием сценария найдите покрытие через `rg` в `tests/`. Не дублируйте существующий бизнес-путь или проверку ради количества тестов.
- Стройте каждый тест по AAA (Arrange–Act–Assert): отделяйте подготовку, одно целевое действие и проверки понятными блоками и Allure-шагами.
- Каждый тест должен быть атомарным и независимым от порядка запуска, общей Appium-сессии и данных, оставленных другим тестом.
- Page Object из `pages/` не импортируют ничего из `tests/`. Модули `utils/` не импортируют ничего из `pages/`. Устраняйте циклические зависимости переносом нейтрального кода в подходящий нижний слой, а не обратным импортом.
- Не полагайтесь на экран, оставленный предыдущим тестом. Сброс состояния приложения (`terminate_app`, `activate_app`, `pm clear`) выполняется только через управляемые pytest-фикстуры или утверждённые helper-методы.
- Если в проекте появится реальный API-клиент или управляемая тестовая БД, создавайте предусловия через него или фикстуры. Не добавляйте вымышленные API/БД-слои и не обходите UI без отдельной задачи.

## Фикстуры, данные и конфигурация

- Инициализацию драйвера, авторизацию, teardown и общие предусловия размещайте в pytest-фикстурах (`conftest.py`) или в явно названных fixture-модулях.
- Статические публичные demo-значения хранятся в `config/test_data.py`. Не копируйте их в тесты и Page Object.
- Для уникальных полей используйте Faker или отметку времени только если сценарий и приложение действительно поддерживают создание таких данных; добавление зависимости требует отдельного согласования.
- URL Appium, таймауты, capabilities и устройства берите из `config/` и выбранного `--device`, а не хардкодьте в тестах или Page Object.
- Секреты, токены, реальные учётные данные и персональные данные берите только из переменных окружения или утверждённого секрет-хранилища. Никогда не печатайте, не прикрепляйте и не коммитьте их; `.env` и `.env.*` остаются вне Git.

## Allure, Qase и диагностика

- Для каждого нового или существенно изменённого UI-теста добавляйте `@allure.feature`, `@allure.story` и `@allure.title` с ясным бизнес-описанием на русском или английском, а также подходящие pytest-маркеры.
- Повторно используемые UI-действия оформляйте `@allure.step` в Page Object. Сценарные действия, проверки и lifecycle-операции оставляйте явными `with allure.step(...)` в тесте.
- Если сценарий связан с существующим Qase case, используйте его подтверждённый `@qase.id(...)`. Не придумывайте ID и не меняйте Qase удалённо без отдельного разрешения.
- При падении сохраняйте существующую диагностику из `conftest.py`: screenshot, page source и Android logcat. Для Android не подменяйте её browser URL или browser-console логами.
- Не оставляйте в коде `print()`, `breakpoint()`, временные дампы или отладочные вложения после исследования проблемы.

## Генерация черновиков из Qase (`tools/generate_from_qase.py`)

- Инструмент забирает строго один кейс за запуск (по `--case-id` или первый со статусом `To be automated`) и сохраняет черновик в `artifacts/qase-generated/`.
- Сгенерированный тест обязан содержать подтверждённый `@qase.id(<id>)` и маркер `@pytest.mark.ai_generated`.
- Если для шагов кейса в `pages/` не хватает методов или локаторов, агент не добавляет вызовы драйвера в тест, а возвращает список пробелов Page Object (`missing_methods`).
- Черновики из `artifacts/qase-generated/` не коммитятся в Git и переносятся в `tests/` только после ревью человеком и прогона на эмуляторе.

## Защищённые операции и CI

- `tests/lifecycle/test_crash_demo.py` запускается только при явном `--run-crash-demo`. Не добавляйте этот флаг в общие команды, CI или проверку перед коммитом.
- Не обновляйте `tests/visual/baselines/` автоматически, скриптом или как побочный эффект теста. Обновление возможно только отдельным изменением после ручного просмотра baseline, actual, diff и метрик для конкретного device profile.
- Не меняйте файлы в `.github/workflows/`, не добавляйте jobs и не меняйте `schedule`/cron без отдельной задачи и явного согласования. Не запускайте вручную платный или удалённый pipeline без разрешения.
- Не отправляйте Telegram-уведомления из локальной работы агента. Существующая интеграция использует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` только в утверждённом CI-контексте.

## Глоссарий домена

- **Catalog / Products** — экран списка товаров приложения Sauce Labs My Demo App.
- **Product card** — экран деталей выбранного товара, а не плитка товара в каталоге.
- **Cart** — корзина с выбранными товарами и входом в Checkout.
- **Shipping** — форма доставки: имя, адрес, город, страна и индекс.
- **Payment** — форма платёжных demo-данных после Shipping.
- **Review Order** — экран проверки заказа перед `Place Order`.
- **Standard user** — публичный demo-пользователь из `config/test_data.py`.
- **Lifecycle scenario** — проверка поведения приложения при Back, блокировке, фоне или системном уведомлении.
- **Crash demo** — намеренно падающий демонстрационный сценарий; не является регрессией.
- **Device profile** — именованная конфигурация `pixel_api31` или `small_phone_api34` с собственными UDID, портом и результатами Allure.

## Circuit breaker при отладке

- Если тест, сборка или проверка падает три раза подряд после ваших изменений, остановитесь. Не добавляйте четвёртый обходной патч.
- Сообщите пользователю: точную команду, три наблюдаемых симптома или краткую хронологию попыток, релевантный фрагмент traceback/logcat без секретов и свою гипотезу о первопричине.
- Не скрывайте проблему через skip, xfail, удаление assert, ослабление проверки, более долгий `sleep` или изменение несвязанного общего слоя.

## Стиль и типы

- Для новых и изменяемых методов в `pages/` и pytest-фикстур добавляйте type hints для всех параметров и возвращаемых значений.
- Имена: тестовые файлы и функции начинаются с `test_`; Page Object классы заканчиваются на `Page`; константы локаторов используют `UPPER_SNAKE_CASE`.
- Следуйте PEP 8 и существующему стилю. Не добавляйте новый линтер, formatter или массовое форматирование без отдельной задачи.

## Самопроверка перед сообщением «Готово»

- Дифф соответствует поставленной задаче и не включает рефакторинг, удаление тестов или изменения общего слоя без согласования.
- Нет новых хардкодов URL, таймаутов, credentials, test data или device settings: им место в `config/` либо переменных окружения.
- Все новые повторно используемые UI-действия имеют `@allure.step`; сценарные действия и проверки имеют понятные Allure-шаги.
- Новые или изменённые тесты сохраняют AAA, независимость, устойчивые локаторы, type hints и подтверждённые Qase ID.
- Выполнены релевантные проверки; непроведённые из-за отсутствия окружения проверки указаны явно, без заявления об успешном UI-прогоне.

## Git, PR и обязательная проверка

- Не изменяйте `main` напрямую. Для каждой задачи используйте отдельную ветку с коротким осмысленным именем и готовьте Pull Request в `main`.
- До коммита просмотрите `git diff`, выполните `git diff --check` и убедитесь, что не добавлены секреты, отчёты, логи, screenshots, page source или другие generated artifacts.
- Не используйте `git add .` или `git add -A`: добавляйте в индекс только явно перечисленные ожидаемые файлы. Никогда не индексируйте `allure-results*/`, `allure-report/`, `artifacts/`, `.pytest_cache/`, `.venv/`, `.env*` или `*.log`.
- Для изменения unit/helper-кода запускайте затронутые unit-тесты и `python -m pytest --collect-only -q`.
- Для изменения Page Object, фикстур, UI-тестов, профилей или visual comparison дополнительно запустите затронутый набор на явно выбранном доступном профиле (`pixel_api31` или `small_phone_api34`) с доступными Appium и эмулятором. Если окружение недоступно, не заявляйте, что UI-набор прошёл: зафиксируйте точную невыполненную проверку в PR.
- Перед commit/push/PR сообщите пользователю результат проверок и все ограничения; выполняйте эти внешние действия только после его явного подтверждения.
