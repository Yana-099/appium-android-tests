# AI-анализ артефактов падения — дизайн

## Цель

Добавить к существующему Appium/pytest/Allure-проекту безопасный post-processing анализ упавших UI-тестов. Он должен превращать уже собранные screenshot, XML page source, logcat и сведения Allure/pytest в короткий, доказательный root-cause summary и практическое предложение исправления (в том числе возможного locator или Page Object), не добавляя UI-сценариев и не влияя на исход pytest-run.

## Контекст

`pytest_runtest_makereport` в `conftest.py` уже прикладывает к failed call-phase тесту screenshot, XML и logcat; для `crash_demo` выбирается crash-only logcat. Allure result JSON хранит метаданные теста, traceback и ссылки на эти вложения. CI архивирует `allure-results/` и `artifacts/`.

## Выбранный подход

Отдельный CLI `python tools/analyze_failure.py --results <dir>` читает один последний упавший raw Allure result после pytest. Он не вызывается из pytest hook, поэтому недоступный API, сеть или медленный модельный ответ не меняют результат теста. CLI запускают локально как демонстрацию AI-анализа одного падения.

Рассматривались также inline pytest hook (немедленное Allure-вложение, но замедляет и связывает тестовый прогон с сетью) и CI-only summary (изолированно, но неудобно локально и хуже интегрируется с Allure). Выбранный локальный post-processing лучше всего показывает AI-составляющую без добавления новой нестабильности в тестовый прогон.

## Осознанно исключённые проверки для MVP-демо

Цель этой версии — на одном реальном failed-тесте показать полный путь: существующие артефакты → очищенный контекст → Structured Output от модели → короткая рекомендация человеку. Поэтому следующие production-oriented механизмы считаются для демо нецелесообразными и не реализуются:

- дедупликация массовых падений и `duplicate_of`;
- лимит `--max-failures` и пакетная обработка всего suite;
- CI-шаг, GitHub Secrets и автоматическая публикация результата;
- автоматическое изменение locator/Page Object по предложению модели.
- mock/fake transport и отдельное тестирование сетевого клиента: для демо достаточно ручного smoke-запуска с ключом и без него.

Они не потеряны: это возможное развитие после MVP, если проекту понадобится регулярный анализ массовых CI-падений. В текущей версии достаточно одного входного инцидента, Markdown-результата `artifacts/ai-report.md`, вложения **AI failure analysis** в Allure и ручного ревью рекомендации.

## Вход и подготовка контекста

CLI находит последний по времени Allure `*-result.json` со статусом `failed` или `broken` и берёт имя, status details, traceback и распознаваемые attachments. Screenshot, XML и logcat находятся по `source` в каталоге results.

Перед передачей поставщику:

- секретоподобные значения, Bearer/API-key токены, пароли и значения поля password заменяются на `[REDACTED]`;
- logcat и traceback ограничиваются по длине, чтобы не раздувать контекст;
- XML превращается в компактное дерево только значимых, видимых UI-узлов: `class`, `resource-id`, `text`, `content-desc`, state и `bounds`; пустые некликабельные узлы с нулевой площадью исключаются;
- screenshot отправляется по умолчанию, чтобы demo показывало визуальное доказательство; `--no-screenshot` отключает передачу. Это допустимо только потому, что проект использует публичное demo-приложение; для реальных данных флаг должен быть выключен.

В API отправляется текст ошибки/traceback, сжатый XML, screenshot и короткий очищенный фрагмент logcat, если в нём есть признаки ошибки. Контекст ограничивается для предсказуемой стоимости одного запроса.

## Поставщик и контракт

Первый и единственный поставщик — OpenAI Responses API. Ключ читается только из `OPENAI_API_KEY`; в исходниках, result JSON, логах и Markdown он не сохраняется. Имя модели настраивается `AI_FAILURE_MODEL`, с документированным значением по умолчанию. Реализация использует стандартный HTTP-клиент Python, чтобы не добавлять зависимость и не импортировать SDK при запуске без ключа.

Запрос использует Structured Outputs: `text.format` с `type: json_schema`, `strict: true`, required properties и `additionalProperties: false`. Короткий ответ содержит ровно три поля: `root_cause` (причина), `evidence` (признаки в XML/screenshot/logcat) и `suggested_fix` (практическая правка теста, locator или Page Object). Отказ, incomplete response, недопустимый JSON и HTTP/network error перехватываются базовым `try/except`, выводят понятное сообщение и не завершают CLI ошибкой.

## Выход

Результат красиво выводится в консоль и сохраняется ровно в один файл `artifacts/ai-report.md`. Затем CLI добавляет тот же Markdown как вложение **AI failure analysis** к проанализированному Allure result. При отсутствии ключа или проблеме сети консоль, файл и Allure-вложение содержат краткое объяснение, а CLI возвращает 0.

## Безопасность

Ключ передаётся только через `OPENAI_API_KEY`; при отсутствии ключа скрипт создаёт объясняющий результат и завершается успешно. Запросы к Responses API используют `store: false`. Screenshot включён для публичного demo-приложения, но может быть отключён `--no-screenshot`. Никакие секреты, API-ответы с ключом или исходные неочищенные контексты не выводятся в консоль.

## Не входит в объём

Генерация TMS-кейсов, новые UI-тесты, изменение device profiles/мультиустройств, Telegram-логика, CI-интеграция, массовый анализ, отдельные mock/fake transport и автоматическое изменение locator/Page Object по ответу модели. Рекомендация AI всегда остаётся предложением для ревью человеком.
